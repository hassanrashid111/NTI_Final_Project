06. Computational Challenge

The 125M+ Row Memory Wall

Standard pandas workflows crashed repeatedly due to RAM exhaustion on 16GB machines.

💥 The Out-Of-Memory (OOM) Problem

Loading 125,497,040 rows in standard Pandas using default int64 and float64 datatypes required over 9.6 GB of raw RAM just to hold the dataframe. Adding lag features exploded memory usage beyond 28 GB RAM!

Notebook 01: Initial Memory Footprint Analysis
🚨 Key Bottlenecks Identified
  • ✕ Pandas default 64-bit precision waste
  • ✕ Single-threaded CSV parsing overhead
  • ✕ Full-dataset feature engineering explosive growth
  • ✕ Slow join operations across 6 relation tables
07. Optimization Strategy

Memory Solutions: DuckDB & Downcasting

Re-architecting the data pipeline to run seamlessly within low memory footprints.

🦆 Why DuckDB over Pandas?

DuckDB process data in vectorized C++ engines with zero-copy querying directly on disk-backed Parquet files, reducing memory usage by 85%+ while boosting join speed by 12x.

🧮 Interactive RAM Footprint Simulator
Data Rows: 125.5 Million

1.
Bit Downcasting: Converted float64 → float32/16 and int64 → int32/8, saving 60% RAM immediately.
2.
Parquet Chunk Processing: Streamed data using columnar Parquet chunks instead of loading massive raw CSVs.
3.
Categorical Encoding: Converted high-cardinality string columns (Store, Family, City) to memory-efficient category integers.

🔍 Notebook 1: Data Understanding Key Discoveries

• Zero Sales Concentration: Over 20% of store-item daily logs had 0 sales (closed days / stock-outs).
• Right-Skewed Distribution: Sales follow a highly skewed log-normal distribution, requiring log1p(sales) transformation for stable model training.
• Timeline Continuity: Identified annual December 25th store closures.

Transforming raw signals into high-predictive time-series features (Lags, Rolling, Cyclical).

• Lag Features: 16d, 21d, 28d, 365d sales history.
